# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

QuizMe is a Kahoot!-style live classroom quiz where points come from confidence, not speed: **Confidence Bidding** (wager a % of your score seeing only category + difficulty), **Safety Net** (the bottom 30% unlock a one-time Double Down or Shield), **Active Side-Bets** (after answering, see anonymous live class stats and bet on whether the class majority is right) and a **Group mode** (random balanced groups that decide by vote). Points never depend on response time; timers only pace the game.

It is built and tested (solo and group games, quiz builder, calibration report, sounds, three themes). [README.md](README.md) is the design spec and source of truth: scoring formulas, data model, security-rules contract and a "Decisions to confirm" list of assumptions the user has not confirmed yet (surface them, don't silently change them). Update the README in the same change when behaviour or the data model changes.

It is one of the edutools apps: a static site on GitHub Pages (plain HTML/CSS/ES modules, no build step, no server, no Firebase Hosting) using the shared Firebase project `edutools-7c110` — Realtime Database + Anonymous Auth.

## Commands

- `npm start` — static preview server (`tools/serve.mjs`, port 5173, `PORT=8080 npm start` to change). Host: `/admin.html`; players: `/student.html?room=CODE`.
- `npm test` — unit tests, `node --test "tests/*.test.js"` (Node 22+, no dependencies). This is what CI runs. One file: `node --test tests/<name>.test.js`; one case: add `--test-name-pattern="<regex>"`.
- `npm run test:rules` — `tests/rules` against the Database emulator (needs Java; local only). The files run one at a time (`--test-concurrency=1`) because each clears the same emulator database. `flow.test.js` plays whole solo and group games with `js/engine.js` as the host, so a change to the engine or the rules is checked against the other. A write of `{}` or `null` is a delete, which `.validate` never sees.
- `npm run test:e2e` — `tests/e2e/run.mjs`: real pages in headless Chrome (a host and phone-sized players) against the Auth + Database emulators. Needs Java and Chrome or Edge (`CHROME_PATH` overrides detection); screenshots land in `tests/e2e/shots/`. Keep two habits: wait for each screen before pressing the next host button (the host ignores a click while a write is in flight), and don't assert on timers in a window that is behind others (Chrome throttles it).
- `npm run emulators` — then add `?emulator` to a page URL on localhost to use them instead of the real project. The namespace `demo-quizme-default-rtdb` is hard-coded in `js/firebase.js`; change it together with `--project demo-quizme` in `package.json`.
- Deploy: push to `main`; `.github/workflows/pages.yml` runs the unit tests, then `cp`s a fixed list (`index.html admin.html student.html css js assets`) into `_site/`, so every path must exist and a new top-level runtime file must be added to that list. The workflow does **not** deploy `database.rules.json`.
- On Windows, `firebase-tools` can leave the emulator's `java` process holding port 9000 after a run (seen in `edutools_cuteworld`); stop only the process listening on 9000 or 9099 before rerunning.

## Architecture

- **No server: the host's page is the coordinator.** `js/host.js` watches the room and, every 250 ms and after every change, asks the pure `js/engine.js` (`autoStep`) what to write next; the host's buttons call `advance`, `finishPatch` and `shufflePatch`. It is a reconciler that keeps no game state: everything is derived from the database (`cur` and its deadline), so a refresh resumes the game. It acts only once every watcher has reported (a half-loaded picture must never score a question), writes one atomic multi-path `update()` per step, and on a refused write pauses for 4 s and shows a banner (usually the rules are not published). Players are untrusted: rules let them write only their own profile, vote, bid, answer and side-bet, once, in the right phase, before the deadline plus 2 s. The host is the creator's anonymous uid in `meta/owner`; its room code is kept in localStorage (`qm.admin.room`), so clearing browser data loses control of a live room.
- **`engine.js` is pure** (snapshot in, patch out; `TS` stands for `serverTimestamp()`), which is why the rules tests can feed its patches to the emulator. Never compare database values as JSON text: key order differs (`sameStats`).
- **A "subject" is a uid (solo) or a group id `g1`, `g2`, … (group mode).** Scoring is keyed by subject. In group mode the host resolves members' `vote/<qid>/<subject>/<uid>/<step>` into the same `bid`, `ans` and `side` nodes a solo player writes, so scoring never knows the mode.
- **Secrecy invariants any new data path must keep:** the answer key lives only in owner-readable `quiz/<qid>` and reaches players only through `res/<qid>` at reveal (never in `cur`); `stats/<qid>` is readable only by subjects that already answered; a group's `vote` nodes are readable only by that group and the owner; `score`, `perk` and `out` are readable only by their subject (ranks are private), and `res/<qid>` can be written once, which is what stops a second host tab scoring a question twice.
- **The phone** (`student.js`) keeps one shared state `S`, fed by watchers that follow the subject and the question (`sync()` swaps them, and nothing renders until the new ones have reported). `student-views.js` has one view per phase, `{ el, update(), flush() }`: `update()` repaints from `S`, and `flush()` sends a choice made but not locked in just before the deadline (the host waits 1.2 s after a deadline for it).
- **Module boundaries:** `js/firebase.js` is the only file that names the SDK URL and version (12.19.0 appears in four URLs there; bump them together) and re-exports `firebase-database.js`, so import `ref`, `onValue` and the rest from `./firebase.js`, never from the CDN. `js/room.js` is the only file that reads or writes the database. `scoring.js`, `decide.js`, `engine.js`, `grouping.js`, `codes.js`, `quiz.js`, `report.js` and the note data in `sounds.js` are pure (no DOM or Firebase) so CI can test them. `ui.js` holds the DOM helpers: use `fill(el, …)`, not `replaceChildren`, which takes no arrays and prints `false` as text.
- **Styling:** `css/style.css` defines the three themes as tokens: black is `:root`, Spruce and Light are `html[data-theme=…]`. Never hard-code a palette colour: use or add a token (`tests/theme.test.js` fails if a theme misses a surface token or an old colour variable comes back). The stake dial's colour comes from `--p` through `color-mix` on the theme's ramp. Every page has a tiny script in its `<head>` that applies the saved theme before first paint, which the same test keeps in sync with `js/theme.js`. Big-screen views must fit a 1366 × 768 projector without scrolling (the e2e test checks each one).
- **Sound:** only the host's page plays sound (Web Audio, no files); phones stay silent. The `questionNotes(n)` sting plays on a live bid → answer change (not when the page loads into a game), and the looping `musicAt(step)` tune plays while the answer clock runs. The tune is reconciled like everything else: the 200 ms timer in `admin.js` that moves the progress bar calls `sounds.music(on, { n, hurry })` on every tick with what should be happening (answer phase, time left, under 5 s), and `createSounds` only starts, quickens or stops when that differs; a scheduler hands notes to the audio clock 0.75 s ahead. `createSounds({ AudioContext })` accepts a fake context, which is how `tests/sounds.test.js` checks the scheduler (with `mock.timers`). The on/off choice is `qm.sound` in localStorage.
- **One Firebase project, one rules file, many apps.** `database.rules.json` holds every edutools app's block (`sessions`, `boards`, `polls`, `mindmaps`, `worlds`, `whiteboards`) and now QuizMe's `quizzes`. Deploying the file replaces the whole project's rules, and each sibling repo keeps its own copy, so the siblings' copies are behind this one until the `quizzes` block is copied back. Compare with the live rules before publishing. Follow the rule conventions (see `boards` and `worlds`): `$code.matches(/^[A-HJKMNP-Z2-9]{6}$/)`, a `meta` that only its `owner` can rewrite, `$other` → `.validate: false`, and an owner-only read at `$code` with children opened one by one.
